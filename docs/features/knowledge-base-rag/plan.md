# Implementation Plan: Knowledge-Base RAG for the Question Writer (Slice 8a)

## Overview
Split the 790-line `interviews_turn.py` without changing behavior (part 1), then add a retrieval layer: curated markdown notes are embedded into Postgres with pgvector, and at interview start up to 6 are chosen for the role, level and job description, saved with the interview, and passed to every main-question write as delimited data (part 2). Concepts 2, 8, 9, 12; the habit from Slices 5 and 6 is that each step ends with a number.

## Architecture & Design
Part 1 is a mechanical move: types, limits, log helpers, the decide step, the blocking write and the streaming write each get their own file in `app/modules/interviews/ai/`, and `Interviewer` keeps its constructor and public methods as a thin orchestrator. Part 2 follows the existing layers. `app/core/ai/` gains an `Embedder` interface (like `LLMProvider` and `Transcriber`), a fake, a small native Google client built on the already installed `httpx` (the OpenAI-compatible endpoint serves embeddings but was not shown to accept task types; the native one accepted task types and a reduced size on your key), and a factory built in the app lifespan. A new `KnowledgeRepository` (separate from `InterviewsRepository`) owns note queries; a retrieval service owns the vector / filter / skip ladder; the start flow in `InterviewsService.start` calls it after `_summarize`, then saves the chosen notes in the same transaction as the session (`InterviewsRepository.start`). Answer turns reload the saved notes in `prepare_answer`, so the JSON and streaming routes both get them from one place. Three new tables: `knowledge_chunks`, `knowledge_chunk_scopes` (one row per role and level a chunk applies to, so the filter is plain portable SQL) and `interview_session_chunks`. The vector column is a portable type: pgvector `Vector(768)` on Postgres, a JSON list on SQLite, so `create_all` and the whole existing suite keep working; on SQLite the similarity is computed in Python, on Postgres by `<=>`. In code and prompts the new text is always called **reference notes** (`ReferenceNote`, `<reference_notes>`), never bare "notes", because "notes" already means the per-turn running notes in the context code.

5. **Note format, validation, chunking (pure).** `utils/interviews_knowledge_utils.py`. A note is a markdown file with a small header between `---` lines (roles, levels, source), parsed by hand with Pydantic validation (no YAML dependency); each `##` section is a chunk, its heading gives the competency, and the hash covers header values and section text. Failures raise a corpus error that names the file: unknown role or level, missing or empty header value, missing source, empty section, a section with no heading. Data-validation rules from the vector-embedding guidance: reject zero-width and other hidden characters, cap section length, and list instruction-like phrases (for example "ignore previous instructions") as warnings in the ingest output, because posting-derived text is third-party. A corpus check requires at least one third of the notes to have a source other than drafted. Also here: the query-text builder (summary, else the job description as entered, else none; blank counts as none), the seeded filter-mode picker, cosine similarity, and the delimiter-neutralising of note text. — Test: first. Seams (user-confirmed): `parse_note`, `load_corpus`, and the pure helpers. Slices, one behavior each: a valid note gives chunks with competency, scopes and a stable key and hash (AC4); each invalid header or section case names the file and writes nothing (AC4); hidden characters rejected and an injection phrase warned (AC4 extended); two chunks with equal text but different headers hash differently; the one-third rule; query text rules (EC1-EC3); the seeded picker returns the same notes for the same id and may differ for another (AC13).
6. **Ingestion and CLI.** `repositories/interviews_knowledge_repository.py` (upsert, retire, reference count, active list) and `services/interviews_knowledge_service.py` with `ingest_corpus(chunks, embedder, repo, ...)`: compare hashes to stored active rows; embed only new chunks as documents, paced for the free-tier limit with an injectable sleep; commit per chunk so a failure keeps what was stored and a re-run finishes the rest; a changed section becomes a new row and the old one is retired; rows referenced by any interview are never deleted or edited; unreferenced retired rows are removed at the end; rows with another model name are re-embedded; a vector of the wrong size refuses before any write. Counts are returned (new, changed, unchanged, retired). `tooling/interviews_knowledge_ingest.py`: `main(argv, embedder=None)` in the style of the eval runners, printing counts, the file and reason on failure, and exiting non-zero. — Test: first. Seam (user-confirmed): `ingest_corpus`, and the CLI `main` with the fake embedder. Slices: first run stores all and counts (AC6); second run makes zero embed calls (AC6, EC11); one edited section makes exactly one call and retires the old row (AC6); a referenced old row is kept (AC7, EC10); a removed note retires (EC12); failure partway keeps stored chunks and a re-run completes (EC13); wrong size refuses with nothing written (AC8, EC14); other model name re-embeds (AC8, EC15).
7. **Retrieval service.** `services/interviews_retrieval_service.py` and repository queries. `retrieve(...)` returns the mode, the chosen reference notes with rank and score, and an outcome code. Ladder: LLM off gives skip `llm_off`; no usable job description gives filter mode (no embed call); otherwise release the DB read, embed the query within the cap, then query and apply the threshold; any embedder error, timeout, rate limit, missing embedder, size mismatch or empty result degrades to filter mode with `retrieval_degraded:<reason>`; no eligible chunk (including an empty corpus) skips with `no_match`; a database error skips with `db_error`. Role and level come only from the interview setup. The repository has the eligible-chunks query (scope filter, active, corpus order) and the nearest query: `<=>` ordering on Postgres, Python cosine over the eligible rows on other dialects. Logs carry ids, counts, ranks, scores, mode, model, latency and codes only; a `tracer.step("retrieval", metadata=...)` records the same. — Test: first. Seam (user-confirmed): `RetrievalService.retrieve` with the fake embedder and SQLite. Slices: vector mode order, filter, k and threshold with scripted vectors (AC11, EC4, EC5); embedded text equals the summary or the text as entered (AC12, EC2, EC3); no job description or blank makes zero embed calls and is stable per id (AC13, EC1); each degrade reason (AC14, EC6, EC7, EC14); each skip reason (AC15, EC4, EC8, EC9, EC18); a slow fake is cut at the cap (AC19); an instruction in the job description cannot change eligibility (AC22, EC16); captured logs and the tracer contain no query text (AC20). The opt-in Postgres test asserts that the real `<=>` ordering equals the Python ordering on the same vectors.

## Blockers & Resolutions
- Local Postgres has no pgvector -> you run the Docker image (Step 4 documents it) before Steps 4's migration check, 6's real ingest and 12.
- Corpus material and review -> Step 11 gate; code steps 2-10 use tiny test corpora.
- Production Postgres support for `vector` -> unknown; verify before deploying (the migration fails loudly otherwise).
- Embedding assumptions -> verified on your key (native task types and 768 size, 3072 default; OpenAI-compatible endpoint also serves embeddings but task types not shown).
- SQLite cannot hold a vector column -> the portable type.
- Edge cases -> all mapped above; EC26 (notes push input over the limit) is new.

## Trade-offs & Rationale
- Native Google client over the OpenAI-compatible endpoint -> needed for task types and the reduced size; uses the installed `httpx`, so no SDK.
- 768 over 3072 dimensions -> verified, smaller, enough at about 100 chunks; changing later means a migration and re-ingest.
- Scope rows over JSON arrays for roles and levels -> plain SQL filter on both databases and a real index, at the cost of one more table.
- Portable vector type with a Python path on SQLite -> keeps the whole suite unchanged; the opt-in Postgres test guards the real path. Running every test on Postgres would be one path but a larger infrastructure change.
- Two new prompt files, used only when an interview has notes -> no-notes behavior stays byte-identical, and the eval arms compare cleanly; the cost is two files to keep in step.
- Notes in the stable prefix and omitted for follow-ups -> cacheable between main questions; follow-up calls lose that prefix, which is accepted.
- Retrieval at start, saved per interview -> reproducible and traceable; per-turn retrieval is out of scope.
- Simulator uses the text format only -> comparable across arms; `interviewer_v6_json` is covered by unit tests and the existing per-turn cases, not by the arms (a known limitation).
- No framework (LangChain etc.) -> keeps the steps visible and the existing deadline, tracing and fakes in charge.
- Ingest as a CLI, not an endpoint -> no new attack surface and no permission to design.

- Added a stable `note_key` per chunk, because chunk ids are random per environment and eval labels need stable names.

The spec's "46, 23 and 21" is corrected. `Interviewer.plan_write` and `settle` stay as thin delegates; `settle` takes `budget_seconds` as a parameter.
