# Implementation Plan: Interview Feedback and Scoring (Slice 6)

## Overview
After an interview is completed, one on-demand endpoint scores it with a validated score call, stores the scores, then writes the coaching text with a second call, so the model judges and writes while the code verifies the evidence, computes the overall and owns every state (concepts 4, 5, 11).

## Architecture & Design
Three new modules in `app/modules/interviews/`, one responsibility each, following the existing pure / LLM / DB split: `interviews_feedback.py` is the pure contract (pre-check, score-reply validation with quote verification, overall, write-text parser, template text, stored-result model); `interviews_feedback_turn.py` holds the two LLM steps with one shared `Deadline`, retries and usage (the sibling of `interviews_turn.py`, reused by the eval runner); `interviews_feedback_controller.py` does the database work (ownership, claim, takeover, store, responses). The `ContextManager` gets two new tasks (score reads the whole interview, write reads only scores and evidence). One new table `interview_feedback` with a unique `session_id` is the guarantee behind "once per interview"; the claim is a compare-and-swap like `record_turn`. The POST is a sync route (threadpool), like the JSON answer route, and no DB transaction is open during an LLM call (`release()` first).

## Implementation Steps
1. **Constants, settings, errors, permission.** In `interviews_constants.py`: `FeedbackStatus`, `TextSource`, a `Criterion` enum, the criteria per category (behavioral: structure, specificity, ownership, outcome; technical: correctness, depth, trade_offs, clarity), the 1-5 scale, the substantive-answer threshold (15 words) and share (one half), quote bounds (10-200), at most one evidence item per criterion (so at most four per question), a reason limit of about 120 characters and the text-slot limits, task names and prompt versions, the score input limit (estimated tokens, sized for the largest allowed interview) and the default answer cap, and the POST limit per minute next to `TRANSCRIPTIONS_PER_MINUTE`. In `config.py` (and `.env.example`): feedback time budget (60 s), stale margin (30 s), score max tokens (about 6,000: the largest interview needs about 4k output tokens even with the evidence cap, and a cut-off reply is invalid JSON), write max tokens, score temperature. In `errors.py`: `InterviewNotCompletedError`, `FeedbackInProgressError` (409), `FeedbackNotFoundError` (404), `FeedbackFailedError` (502), `FeedbackUnavailableError` (503), each with its own code. In `auth_constants.py`: the `interviews:feedback` permission added to the shared interview set, so `admin` and `user` hold it; `tests/modules/auth/test_permissions.py` hard-codes that set (its `INTERVIEW_PERMISSIONS`), so add the new permission there too or two existing tests fail. — Test: skip (config), except the update to `test_permissions.py`; behavior is covered by Step 7.
2. **Pure contract.** `interviews_feedback.py`: thread building from stored rows (a main question, its follow-ups, their answers); `assess_evidence` (the code pre-check); `parse_score_reply` (strict Pydantic with `extra="forbid"`, integer scores 1-5, exactly the category's criteria, every main question once and in order, at least one and at most one-per-criterion evidence items per question, quote 10-200 characters found in that same thread ignoring case and whitespace, reason within its limit, optional `enough_evidence=false`); `compute_overall` (mean of all criterion scores, rounded half up to one decimal with `Decimal`, not `round()`, whose banker's rounding and float storage turn 3.25 into 3.2; ignores any total the model states); `parse_write_reply` (labelled plain-text sections, item counts, length limits, no markdown, a note for every main question); `template_text` (stored scores and evidence reasons to the same slots, with per-criterion tips from constants); a stored-result model that revalidates what is read back. Reason codes only, never raw text. Reuse the fence and JSON loading of `interviews_reply.py` by making `_load_object` public (no cross-module import of an underscore name). — Test: first. Seams (user-confirmed): `assess_evidence`, `parse_score_reply`, `compute_overall`, `parse_write_reply`, `template_text`. Slices, one behavior each: thresholds and the half rule (EC9); a valid reply accepted; not JSON, extra field, score out of range, missing or repeated question, wrong criteria for the category (EC10); quote missing, too short or long, found only in another thread, case or spacing differences accepted, checked against the full stored answer (EC11, EC23); `enough_evidence=false` accepted (EC29); too many evidence items for a question rejected; overall rounding half up (for example 3.25 gives 3.3) and ignoring a model-stated overall (AC9); write parser accepts and rejects (AC15); template covers every question within the same limits (AC13).
3. **Rubric and prompts (data).** `data/feedback_rubric_v1.json`: for each criterion, anchored descriptions for the five levels, with an early / experienced expectation per level group (reuse `LEVEL_GROUPS`); loaded and validated at import so a broken file stops the app at startup, like the bank. `prompts/feedback_score_v1.md` and `prompts/feedback_write_v1.md` in the six-part layout; the score prompt states the data-not-instructions rule, the voice-transcript rule (ignore filler, punctuation and transcription slips, judge content), the closed output shape, the evidence cap and that no total is wanted; the write prompt receives scores as fixed facts and the exact section labels. Each prompt's second line (its role line, before any `{{placeholder}}`) must be unique, because the test `llm` fixture routes calls by that line (`conftest.py`, `_DECISION_MARKER`). I draft all three; **the user reviews the anchors and prompts at the gate in Step 9** before any real-model run. — Test: first for structure; the wording is judged by Step 8-9 evals. Seam: the rubric loader and `load_prompt`, with the six-heading check pattern of `test_context_prompts.py` and a check that every criterion has five anchors.
4. **Context tasks.** In `interviews_context.py`: a feedback-inputs value, a score strategy (stable system prompt with role, level, type and rubric; user messages carry the job description and each thread inside fences, answers capped, nothing droppable, its own input limit; the answer cap is a constructor parameter defaulting to the constant, because answers are already limited to `MAX_ANSWER_LENGTH` = 2,000 characters, so tests build the strategy with a small cap to reach the truncation path) and a write strategy (scores, reasons, quotes, question texts, role and level only; no answers, no job description; no limit). Register both as tasks in `build_context_manager`. Add the new fence tags to `APP_TAG` so untrusted text can't close its own block. Over the limit raises `ContextTooLargeError` as today. — Test: first. Seam (user-confirmed): `ContextManager.build`. Slices: score input fences answers and job description and neutralises closing tags (AC14, EC17, EC18); write input holds no answer text or job description (AC14); an over-cap answer is truncated with the marker and counted, the quotes still verify against the full text (AC21, EC23); too large raises (EC22); the largest allowed interview fits the limit.
5. **LLM steps.** `interviews_feedback_turn.py`: a generator class built like `Interviewer` (provider, context manager, max tokens, temperature, injectable clock) with one `Deadline` shared by both calls. Score step: at most two attempts, a retry only when time allows (`MIN_SECONDS_FOR_RETRY`), invalid reply, empty reply, `LLMError` or a too-large context mean a failure with a reason code and no partial scores; a reply cut off by the token cap (`finish_reason=length`) is logged as its own reason (`truncated`), so a cap that is too low shows up in the numbers instead of as "invalid JSON". Write step: one retry of the write call only; failure or no time left returns nothing so the controller uses the template. Usage and latency summed per step; one `llm_call` line per call through the existing `log_result` / `log_llm_call`, task and prompt version as trace labels; one summary line per generation (outcome, overall, `text_source`, retries, tokens, latency, quotes rejected, answers truncated; no text). The controller wraps a generation in `tracer.trace("interview-feedback", ...)` with ids only as `input` (the answer route puts the answer text there; feedback must not). When the generation ends it sets the trace output with `tracer.set_trace_output` (outcome, overall, `text_source`, scores per criterion; no text) and posts two trace scores with `tracer.score`: `overall` and `quotes_rejected`, so drift over real interviews is visible in Langfuse. Both are no-ops when tracing is off. In `interviews_log.py`, `turns_of` leaves out a request whose calls are all feedback tasks (it is not a turn; its cost is on the feedback row); today any request with `llm_call` lines and no `turn_summary` shows in `interview_report` as a failed (`partial`) turn. — Test: first, through the endpoint slices of Step 7 (scripted `llm`, fake `clock`); the `turns_of` label with one test next to the existing log/report tests.
6. **Data, migration, repository.** `InterviewFeedback` in `interviews_model.py` (UUIDv7 via the mixin, unique `session_id` with cascade delete, status, `enough_evidence`, rubric and prompt versions, `text_source`, `overall`, a JSON result, model and tokens and latency per call, failure reason code, started and finished times). The result uses SQLAlchemy's generic `JSON` (the first JSON column in the project; it works on SQLite and Postgres) and is always assigned a new value, never edited in place, because in-place changes are not tracked. New Alembic revision with `down_revision` `a72345efd4c2` (the current head, found with `alembic heads`; the newest-named file is not the head); applied migrations untouched. Repository methods: read by session, claim (insert, or conditional update of a `failed` row or a `generating` row older than the stale cutoff, the same compare-and-swap idea as `record_turn`), store scores, store text, mark failed, store the insufficient result. **Claim token:** the claim sets a new `started_at` (and returns it); every later update (scores, text, failed, insufficient) is a conditional UPDATE on `id`, `status = generating` and that `started_at`, and returns whether it matched. Zero rows means another request took the row over: the slow request stores nothing and returns the current row. **Stale check in SQL:** the cutoff comparison is part of the conditional UPDATE, never done in Python, because the test SQLite stores datetimes without a timezone and comparing them with an aware `now` raises `TypeError`. Wall-clock time comes from an injected `now` (UTC) so stale takeover is testable; the per-call `Deadline` keeps using the monotonic `clock`. — Test: after for the migration (upgrade then downgrade by hand on the real engine, since tests use `create_all`), including deleting an interview there to see its feedback row go (the test SQLite has no `PRAGMA foreign_keys=ON` and the models have no ORM relationships, so a cascade can't be observed in pytest; pytest only asserts the foreign key is declared `ondelete="CASCADE"`); claim, takeover and the lost-claim case are covered by Step 7.
7. **Controller, schemas, routes, dependencies.** `interviews_feedback_controller.py`: `generate`, with its checks in this order: owned session or 404; completed or 409; read the existing row (`generated` returns it with 200, a fresh `generating` gives 409); LLM configured or 503, no row; claim (losing the insert race gives 409); read the questions and answers into plain values; release the read; pre-check; score step; store; write step or template; store; response. Then `get`. A stored result is returned even when the LLM is off. Response models in `interviews_schema.py` (no usage, versions, model, job description). Two routes in `interviews_route.py` guarded by `require_permissions(interviews_feedback)`: POST returns 201 on first generation and 200 when already generated (same body, no LLM call), GET returns the stored row in any status; `responses=` documents 401/403/404/409/429/502/503. In `interviews_dependencies.py`: the controller dependency, a per-process feedback `RateLimiter` with a swappable getter like the transcription one, and a `now` dependency. `AppError`s map to the structured errors; a `failed` result is a 502 `FEEDBACK_FAILED`. — Test: first. Seam (user-confirmed): `POST` and `GET /api/v1/interviews/{id}/feedback` with the scripted `llm`, fake `clock` and captured-log fixtures. Slices in order: auth, ownership and not-completed errors (AC1, AC2, EC1-EC4); happy path shape and excluded fields (AC1, AC7, AC9); second POST returns 200, same id, zero calls (AC3, EC5); pre-check insufficient with zero calls (AC6, EC9) and the model flag (EC29); invalid score reply retried once, then failed 502, GET shows no scores (AC10, EC10, EC11); provider error and budget exhausted (AC11, EC12); too-large context (EC22); scores stored before the write call (AC12); write fails or invalid twice gives the template while the score call ran once (AC13, EC13); failed then POST again regenerates on the same row (AC17, EC26); fresh `generating` gives 409 and two simultaneous POSTs make one row (AC4, EC6, EC7: tests share one SQLite session, so real parallel inserts aren't possible; a second POST fired from the score fake's `on_call` hook gets 409, like `test_answer_stream.py::test_two_submits_of_one_question_save_one_turn_and_the_loser_gets_an_error_event`, and the insert-conflict branch is tested with a row inserted between the read and the claim); stale takeover with stored scores runs only the write call (AC5, EC8, EC14); a request whose row was taken over stores nothing (EC30); rate limit 429, LLM off 503, and LLM off with a generated feedback still 200 (AC18, EC27, EC28); GET states and 404s (AC16, EC25); injection and delimiter cases (EC16-EC18, AC14); follow-up threads and mixed categories (EC20, EC21); no personal text in captured logs (AC20); with `get_tracer` overridden by a recording tracer, the trace's input holds ids only and its output and scores hold no answer, quote or note text; the foreign key declares the cascade (AC19, EC24; the delete itself is checked on the real engine in Step 6).

## Blockers & Resolutions
- Spec lists the POST rate limit as a setting -> deviation: a constant next to `TRANSCRIPTIONS_PER_MINUTE`, matching the existing pattern (budget, tokens, temperature stay settings).
- Spec orders no checks between LLM-off and the pre-check -> LLM off returns 503 before the pre-check, even for a near-empty interview (simple and matches EC28); an already stored result is still returned (200), because the existing row is read before the LLM check (review fix).
- Plan review against the code (2026-11-05) -> fixed in the steps above: `test_permissions.py` update (Step 1); score max tokens and evidence cap (Steps 1, 2); half-up rounding (Step 2); answer cap as a parameter (Step 4); `truncated` reason, ids-only trace, `turns_of` label (Step 5); claim token, stale check in SQL, cascade checked on Postgres (Step 6); check order and how EC7 is tested (Step 7).
- Found while implementing (2026-11-05) -> `tests/modules/auth/test_me.py` also hard-codes the interview permissions (updated with Step 1); `turns_of` leaves feedback requests out instead of labelling them, because a label would add their cost to the report's turn totals and feedback cost in reports is out of scope (spec); `template_text` takes only the scores and the overall (the threads were never needed); the section labels live in `interviews_constants.py` (the prompt renderer in `interviews_utils.py` can't import `interviews_feedback.py` without a cycle); GET and POST show scores and text only for a `generated` row, so a stale or half-written `generating` row never shows partial scores.
- Global provider limits vs a long score call -> user decided: keep them, measure first (Step 10); fix with data only if the maximum-size run times out.
- Alembic head is `a72345efd4c2`, not the newest-named file -> the new revision is built on the head.
- Existing `llm` test fixture only separates decide calls -> Step 7 helpers route score and write calls too, so existing tests stay unchanged.
- Rubric anchors and expected bands are ground truth -> drafted by me, reviewed by the user at Step 9 before real runs.
- Langfuse sees answers for feedback too (same as turns) -> noted in learnings; decide before enabling tracing in production.

## Trade-offs & Rationale
- Three modules (pure, LLM, DB) instead of growing the 728-line controller -> each is testable alone and the eval runner reuses the first two.
- Store scores before the write call -> a write failure or crash never repeats the expensive call, and takeover can resume.
- A JSON result column, not per-score tables -> nothing queries scores yet; `overall` is a column for later reports.
- Sync route, no 202 and polling -> same shape as the JSON answer route; simpler for the client; the cost is one long request.
- Quote check ignores case and whitespace only -> strict enough to catch invented quotes, loose enough for harmless formatting differences; punctuation changes in voice transcripts may cause rejections, which the evals will show.
- The write call never sees full answers or the job description -> less personal data to the provider, and nothing in it can carry an injection.
- Template fallback copy lives in constants -> the page is useful if the write call fails, at the price of stiff wording.

## Project Rules Applied
- `CLAUDE.md` layers and `interviews_` prefix -> three modules in the feature, routes stay thin.
- UUIDv7 keys, Alembic only, no `create_all` reliance -> Step 6.
- Prompts as versioned data, provider behind an interface, config for model and budgets -> Steps 1, 3, 4, 5.
- Structured output validated, retry then fallback -> Steps 2, 5.
- Prompt-injection safety, privacy, no raw text in logs -> Steps 3, 4, 5, 7.
- Rate limiting and ownership in the controller -> Step 7. Mock the LLM in unit tests, eval set per AI feature -> Steps 7, 8. No commits -> all steps.
- OWASP LLM checklist (llm-security): LLM01 delimiters, rules in code, no privilege from text; LLM02 minimal write input, no text in logs; LLM05 model output is parsed, bounded and never trusted for the overall; LLM09 evidence quotes verified against answers; LLM10 rate limit, input limit, token caps, one shared deadline, at most three score-side calls.
