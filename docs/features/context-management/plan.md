# Implementation Plan: Context Management for the Interview LLM Calls

## Overview
Add a context manager that decides what is sent to the LLM per task. The interviewer turn uses a bounded `window_ledger` strategy by default: stable prefix, last 3 turns in full, older turns as a list of questions with a short running note about each answer, capped older answers, a long job description replaced by a stored summary, and a 5,000-token input limit. The old send-everything behavior stays as `full_history`, which is never trimmed so it remains a true baseline. A baseline token report and eval-runner flags (strategy, model, reasoning effort, summary, notes, repeats) measure the effect. The "before" numbers are recorded before the live default changes, and every comparison uses repeated runs plus a manual quality review.

## Architecture & Design
A feature-agnostic **ContextManager** in `app/core/ai/context.py` holds, per task name, named strategies, a default, and an optional input limit per strategy. `build(task, inputs, strategy=None)` runs the strategy, estimates size (characters divided by 4, per section and total), and, only when that strategy has a limit and is over it, asks the strategy to rebuild with its oldest entries dropped, one at a time. Required parts are never dropped: if they alone exceed the limit it logs and raises a "context too large" error. Every build logs one numbers-only line on `app.llm.context` and returns messages, a report and the prompt version used.

A strategy is a small class with `droppable(inputs)` and `build(inputs, dropped)`. `interviews_context.py` registers `interviewer_turn` (`window_ledger` default with limit 5,000; `full_history` with no limit) and `job_description_summary` (one strategy, no limit). `full_history` is never trimmed, whatever its size, so comparisons against it are honest and it stays the model for a future whole-interview task such as feedback. `full_history` calls the existing `render_interviewer_prompt` and `build_interviewer_messages` untouched, so AC1 holds by construction and it keeps prompt v1 (no notes). `window_ledger` uses `interviewer_v2`: the system prompt carries only per-interview constants; the job description opens the conversation as the same fenced user message on every call; the changing parts (question number, ledger, notes) go in a tagged status trailer appended to the last user message (user-confirmed), present only once there is at least one turn. Tag lookalikes in answers and notes are neutralised.

**Running notes.** The v2 reply is `question`, `category` and an optional `note` describing the latest answer. The parse function accepts a valid question with a missing or bad note (note dropped, reason returned for logging), and still rejects unknown fields. The controller saves the note on the candidate message it describes; `QuestionTurn` gains an optional note, filled from stored messages, and the ledger prints it next to the older question. The first question, the final answer and bank-fallback turns have none.

**Summary.** Made in `start` before the first question, only when the LLM is on and the description is over the threshold; one attempt with its own 10 s cap (user-confirmed); validated by a pure function; stored on a nullable session column; used in place of the original afterwards. Any failure keeps the original.

**Reasoning effort.** An optional argument on the provider call, sent only when given, exposed by the eval runner flag only; the live app does not set it. The controller gets the manager through a dependency (like `get_clock`) so tests can inject a tiny limit.

**Validation.** The eval runner repeats each configuration N times and reports every run plus the aggregate, because one run proves little (the Slice 2 learnings saw 5/6 and then 6/6 on the same cases). Format checks cannot show a quality loss from windowing or notes, so the long-history outputs of each compared configuration are also reviewed by hand against a short quality checklist. Before step 10 switches the live default, step 8 records the "before" snapshot with `full_history`, so any later regression has something to be measured against.

**Quality checklist (steps 8 and 12, applied by hand to each long-history output):** (1) relevant to the role and job description; (2) not a repeat or rephrase of an earlier question; (3) a sensible next topic at the right difficulty for the level; (4) consistent with what older answers said (does not re-ask a point already covered or contradict it); (5) follows the rules (one question, no greeting, no judging). Record pass or fail per item with a one-line reason. An LLM-as-judge stays out of scope.

## Blockers & Resolutions
- `finish=length` not stored -> the eval runner reads it from `LLMResult.finish_reason` and the error's `finish_reason`; no schema change.
- Provider caching unverified -> verified in step 12; the layout ships regardless because it costs nothing.
- Window, summary and notes quality unproven -> compared in step 12 against the step 8 snapshot, with repeats and the manual checklist; reversible by constants or by pointing the task default at `full_history`.
- Baseline distorted by the limit -> `full_history` has no limit and is never trimmed.
- Baseline lost once the default changes -> step 8 records it before step 10.
- Format checks blind to quality loss -> manual checklist on long-history outputs in steps 8 and 12.
- Notes may hurt (error accumulation) -> notes on/off comparison; fallback is question-only ledger entries.
- Reasoning option support is model-dependent -> real call in step 12; omitted where unsupported.
- Summary may not pay for itself, and adds start latency -> measured in step 12; own 10 s cap, falls back to the original.

## Trade-offs & Rationale
- Strategies with `droppable` and `build(dropped)` -> generic trimming without a block/priority framework (deferred until feedback or RAG share a budget).
- Limit per strategy, none for `full_history` -> the baseline stays true and the future feedback task can send everything.
- Snapshot before the switch -> the live default changes before the comparison, so the "before" numbers must exist first.
- Manual checklist instead of an LLM judge -> cheap, no new prompt or model to trust; enough to spot regressions at this scale.
- Trailer in the last user message -> keeps alternation and a stable prefix; app text beside untrusted text is handled by neutralising tags and labelling.
- Notes from the same call, optional and lenient -> no extra call and no retry cost; a bad note never costs a question.
- Constants instead of env settings -> user decision; tuning is a code change guided by the comparison.
- Character-based estimate -> no tokenizer dependency; checked against provider `prompt_tokens` in logs.
- Keep the old builders -> `full_history` is correct by construction and stays a real baseline.
- Reasoning effort only in the eval runner -> measures the output-token lever without changing live behavior.
