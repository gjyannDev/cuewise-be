# Implementation Plan: Interview History List (backend)

## Overview
Add `GET /api/v1/interviews`, a paginated newest-first list of the caller's interviews (all statuses, with `answered_count`), and move the pagination contract that `GET /users` already has into `app/core/` so both lists share it.

## Architecture & Design
Request flow stays route -> controller -> repository. Pagination is shared by composition in a new `app/core/pagination.py`: a `PageParams` dependency (`limit` 1-100 default 20, `offset` >= 0) and a generic `Page[T]` response model (`items`, `total`, `limit`, `offset`). Each feature keeps a named subclass (`UserListOut`, `InterviewListOut`) so OpenAPI schema names do not change. No base repository or base service (decided with the user; ponytail applied inline: only pagination is duplicated, and the interviews query differs from the users one, so a shared `paginate()` query helper would not be reused and is left out).
`answered_count` needs no `GROUP BY`: the repository selects each session with the main-question number of the question at its `current_position` (correlated scalar subquery), and a pure rule in `interviews_utils.py` turns status + `question_count` + that number into the count. A page costs two queries (rows, total) whatever the page size.

## Spec Requirements -> Implementation
- Shared `PageParams` / `Page[T]`, `GET /users` refactored unchanged (AC14) -> Steps 1, 2
- Item/list schemas, no private fields (AC2) -> Step 3

## Implementation Steps
1. **Shared pagination module.** Create `app/core/pagination.py` with the page-size constants (moved from `users_constants.py`), `PageParams` and `Page[T]`. Follow the `GET /users` contract exactly (same bounds, same envelope). — Test: after (the existing users tests are the net; run them first and they stay green)
2. **Refactor `GET /users`.** Route takes `PageParams`; `UserListOut` becomes a subclass of `Page[UserAdminOut]`; the controller builds the page; delete `users_constants.py` once nothing imports it (confirm with a search). Response shape and error bodies must not change. — Test: after (`tests/modules/users/test_list_users.py` unchanged; its OpenAPI-responses test covers the 401/403/422/500 docs)
3. **Interviews schemas.** In `interviews_schema.py` add `InterviewListItemOut` (id, role, level, interview_type, status, question_count, answered_count, created_at; `extra` irrelevant, output only) and `InterviewListOut` (subclass of `Page[InterviewListItemOut]`). Status filter reuses the `SessionStatus` enum, so an unknown value is a 422 for free. — Test: skip (types; exercised through Step 7's tests)
4. **Index and migration.** Add a (user_id, id) index to `InterviewSession.__table_args__` beside the existing partial unique index, and a new Alembic revision on top of head `e3b8f41a6c27` that creates it and drops it on downgrade. Plain ascending columns: a btree serves `ORDER BY id DESC` by scanning backwards (confirmed on PostgreSQL: Index Only Scan Backward). Review the autogenerated file; do not touch applied migrations. — Test: skip (config); verified by upgrade/downgrade run
5. **Repository.** In `interviews_repository.py` add `list_for_user(user_id, status, limit, offset)` (owner filter, optional status filter, `ORDER BY id DESC`, limit/offset, plus the current question's main number via correlated subquery) and `count_for_user(user_id, status)`. Follows the `UsersRepository.list/count` pattern; no business rules here. — Test: first (seam: the HTTP endpoint, see Testing Strategy)
6. **`answered_count` rule.** Pure function in `interviews_utils.py`: completed -> `question_count`; otherwise current main number - 1, never below 0 and never above `question_count`; missing current question -> 0. — Test: first (seam: HTTP endpoint; user chose HTTP only, so no separate unit seam)
7. **Controller and route.** `InterviewsController.list` builds `InterviewListOut` from the repository rows and the rule; route `GET ""` with `PageParams`, optional `status` query, `require_permissions(interviews_read_self)`, explicit 200, 401/403/422/500 documented via the router defaults. Defined next to the other `GET`s; no clash with `/{session_id}`. — Test: first (seam: `GET /api/v1/interviews`)
8. **Verify and close.** `uv run pytest`, `uv run ruff check .`, alembic upgrade -> downgrade -> upgrade, `graphify update .`, tick spec ACs. No commit. — Test: skip

## Blockers & Resolutions
- Spec has no blockers.
- Shared pagination touches `GET /users` -> refactor guarded by unchanged existing tests (AC14).
- Pagination shifting while a user starts a new interview (EC12) -> accepted for offset paging.
- Interview with a missing current question (should not happen) -> `answered_count` 0, never an error.

## Trade-offs & Rationale
- Composition (`PageParams`, `Page[T]`) over base repository/service -> only pagination is truly shared; matches "no speculative abstractions".
- Subclass per feature of `Page[T]` -> stable OpenAPI names, one line each.
- Separate count query -> same as `GET /users`, simple; the cost is two queries, which is fixed.
- Correlated subquery for the current main number instead of `GROUP BY` or a stored counter -> no new column, no extra per-row query.
- HTTP-only seam -> matches existing tests and survives refactors; the rule is covered through its slices.

## Project Rules Applied
- `CLAUDE.md` architecture -> layers, `interviews_` file prefix, shared helpers in `app/core/`, no cross-module repository imports.
- `CLAUDE.md` security -> default-deny permission dependency, owner scoping in the query, `response_model`, no free text or `job_description` in output or logs.
- `CLAUDE.md` FastAPI standards -> explicit status codes, documented errors, paginated list, new Alembic migration only.
- `CLAUDE.md` workflow -> tests plus ruff, `graphify update .`, no commit or push.
